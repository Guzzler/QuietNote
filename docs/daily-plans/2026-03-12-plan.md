# QuietNote Daily Plan — 2026-03-12 (Day 1)

## A. Today's Objective

Fix the conversation reliability problem: implement context window management so QuietNote doesn't silently degrade or break after 10-15 turns of conversation.

## B. Why This Matters

- **User value**: Users in long journaling sessions will get consistent, quality responses instead of degraded or garbled output mid-conversation.
- **Safety value**: Incoherent responses to a distressed user are actively harmful. This is a safety bug, not just a quality issue.
- **Technical value**: The Gemma 2B model has a 4K token context window. Currently, `buildMessages()` sends the entire conversation history with zero truncation. After ~20 exchanges, context silently overflows.

## C. Top 3 Priorities

1. **Context window management** — Create a token estimation + history trimming system so conversations never overflow the 4K context limit.
2. **Fix system prompt role** — Change the system instruction from `role: "user"` to `role: "system"` (WebLLM supports it). This improves instruction-following and frees up a turn slot.
3. **Tool-calling architecture design** — Design (not build) the first tool-calling pattern: client-side emotion extraction → mood log suggestion card. No model-side tool calling due to Gemma 2B limitations.

## D. Concrete Implementation Plan

### Priority 1: Context Window Management

**What to change**: Create `src/utils/tokenEstimator.ts` and refactor `buildMessages()` in `src/App.tsx`.

**Token estimation utility** (`src/utils/tokenEstimator.ts`):
- `estimateTokens(text: string): number` — Character-based heuristic (~3.5 chars/token for Gemma 2B English text)
- `trimConversationHistory(messages, budgetTokens)` — Walk from most recent message backward, accumulate token count, stop when budget exceeded. Always keep at least the most recent user message. Return in chronological order.
- Constants: `MODEL_CONTEXT_LIMIT = 4096`, `RESERVED_FOR_GENERATION = 512`, `RESERVED_FOR_SYSTEM = 200`, `AVAILABLE_FOR_HISTORY = 3384`

**Refactor `buildMessages()` in `src/App.tsx` (lines 28-45)**:
1. Build system message with `role: "system"` (ties into Priority 2)
2. Estimate tokens for system prompt + current user entry
3. Calculate remaining budget for history
4. Call `trimConversationHistory()` with remaining budget
5. Append trimmed history + current entry
6. Return messages array

**Context-trimmed indicator in `src/components/ChatPanel.tsx`**:
- Show subtle "Earlier messages not in context" notice when messages have been trimmed
- Important for user trust — they should know the model may not recall the start of a long conversation

**Dependencies/blockers**: None. Pure logic change.

**How to test**:
- Unit tests for `tokenEstimator.ts` (short/long/empty conversations, edge cases)
- Manual test: Have a 15+ turn conversation and verify responses remain coherent
- Verify crisis detection still triggers correctly after the refactor

**What could go wrong**:
- Token estimation heuristic could be inaccurate for non-English text or code
- Trimming too aggressively could lose important early context
- Mitigation: Conservative budget, start with higher chars/token ratio

### Priority 3: Tool-Calling Architecture Design (Design Only)

**No code changes today.** Document the design for the first tool.

**Proposed first tool: Mood Log Suggestion**

Architecture:
- `src/utils/emotionExtractor.ts` — Client-side keyword/pattern matching (follows `crisisDetection.ts` pattern) to detect emotions expressed in conversation
- `src/components/MoodSuggestionCard.tsx` — Inline UI card after assistant messages showing "Log this mood?" with pre-filled emotion/intensity/context
- User clicks to accept, modify, or dismiss. Accepted entries saved via existing `putMood()` in `storage.ts`

**Why client-side, not model-side**: Gemma 2B is too small for reliable structured JSON tool-call output. Client-side extraction is deterministic and testable.

Design principles:
1. **User-initiated only** — LLM suggests, user confirms with explicit click
2. **Observable** — Every suggestion visible as UI card
3. **Reversible** — Mood entries deletable via Privacy Dashboard
4. **Sandboxed** — Writes only to existing IndexedDB mood store
5. **Minimal** — One tool first, no framework

### Classification
- **Safe to build now**: Mood log suggestion (client-side extraction + UI card)
- **Needs more safeguards**: Any model-generated tool calls, conversation summarization via LLM
- **Should not be built**: Internet access, external API calls, autonomous actions without user confirmation, hidden data writes

## F. Safe Tool Ideas

### 1. Mood Log Suggestion (First Tool)
- **What**: Detect emotions in conversation, suggest logging a mood entry
- **Why safe**: Read-only analysis of already-visible conversation text; write requires explicit user click
- **Permissions**: Write to IndexedDB mood store (existing)
- **Possible misuse**: Over-suggesting could feel intrusive or like surveillance
- **Safeguards**: Minimum message length before suggesting, cooldown between suggestions, dismiss permanently option, session-level disable

### 2. Journal Prompt Recommendation (Future)
- **What**: Suggest a relevant journaling prompt based on current conversation themes
- **Why safe**: Read-only, draws from existing curated prompt database
- **Permissions**: Read from journalPrompts.ts data only
- **Possible misuse**: Could feel manipulative if prompts are poorly timed (e.g., "What are you grateful for?" during crisis)
- **Safeguards**: Never suggest during crisis-detected conversations, respect user's current emotional state

### 3. Session Summary Generation (Future, Needs Safeguards)
- **What**: Generate a brief summary of the journaling session when user ends it
- **Why safe-ish**: Uses the LLM the user is already talking to, summary stored locally
- **Permissions**: Read conversation history, write summary to session in IndexedDB
- **Possible misuse**: Summary could misrepresent what user said; if read later, could cause distress
- **Safeguards**: User must opt-in, summary shown for review before saving, edit/delete capability

**Rejected tools**: Internet search, contact recommendations, diagnosis suggestions, medication tracking, social sharing, therapist matching, AI-generated affirmations without user request.

### Biggest Safety Risk Today

**Context overflow causing incoherent responses during emotional conversations.** A user pouring their heart out in a long session could suddenly receive garbled, contradictory, or nonsensical output because the context window silently overflowed. This is the most likely safety failure today and is directly addressed by Priority 1.

**Best mitigation**: Implement context window management with conservative token budgets and a visible indicator when history is trimmed.
