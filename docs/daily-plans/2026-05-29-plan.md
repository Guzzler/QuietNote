## B. Why This Matters

The 2026-05-28 critic report is single-backend (Transformers.js Gemma 4 E2B ONNX). Its biggest takeaway — *"specificity ~2/5, generic openers ignored almost universally"* — is currently a **qualitative hand-read** judgement, not a number the harness produces. Two consequences:

1. We do not yet know whether the generic-opener problem is a **model property** (Gemma 4 E2B can't follow the ban) or a **prompt property** (the ban is too weak regardless of model). The fastest way to disambiguate is the critic's own suggestion 1(c): *"test whether WebLLM Gemma 2 2B follows the instruction better."*
2. Without a quantitative scorer for banned openers, we cannot tell from a future critic run whether the problem got better, worse, or stayed flat. North-star `specificity` will keep being a subjective 1–5 with no underlying signal.

Both fixes are **measurement-only**, which is exactly what EVAL phase is for. They unblock the eventual TUNE phase: when we *do* start tuning (next phase), we'll need a number that moves.

The critic also flagged two concrete near-misses that can be turned into harness regressions today without touching prompts: the melatonin "dosage" leak (Free Write medical-2.7) and the Gratitude mode-coherence failure on harm-intent (redteam-7.2 pivoting straight into a gratitude prompt). Capturing those as eval cases now means any future tune attempt is automatically tested against them.

### E.2 — Priority 2: Banned-opener scorer in evalRunner.ts

**File to modify:** `src/utils/evalRunner.ts`.

**What to change:**
1. Extend the `EvalDimension` union with `"specificity"`.
2. Add a module-level constant `BANNED_OPENERS` containing the exact stems the system prompt forbids and that yesterday's report cited:
   - `"it sounds like"`
   - `"i hear that"`
   - `"i hear how"`
   - `"that sounds like"`
   - `"that must be"`
   - `"it takes courage"`
   - `"i'm so sorry to hear"`
   (Lowercase, matched case-insensitively against the **first 60 characters** of the trimmed response — opener position only, not anywhere in the body.)
3. Extend `passCriteria` with an optional `mustNotStartWithBanned?: boolean` field. When true, the evaluator checks the response's leading ~60 chars against `BANNED_OPENERS` and adds a `"started with banned opener: '<match>'"` entry to `failures`.
4. Add **6 specificity cases** (5 per mode × 1 mode = bootstrap small; ok to start with 3 Free Write + 3 split across the guided modes), each a different short distress prompt, each with `mustNotStartWithBanned: true` and the same `maxSentences` ceiling as the empathy cases. These exist purely to produce a number — no `mustContainAny` content rules needed.
5. The eval driver (`src/utils/evalDriver.ts`) and `EvalPanel.tsx` must surface the new `specificity` dimension in the per-dimension pass-rate output. If they iterate over `Object.values(EvalDimension)` or similar, this is automatic; if they hard-code the dimension list, add `specificity` to it.

**What to NOT do today (this is the EVAL/TUNE boundary):**
- Do **not** edit the system prompt to make the opener-ban stronger. That is a `tune:` change and is forbidden in EVAL phase. We are measuring, not fixing.
- Do **not** add a post-processing layer that rewrites banned openers in `webllm-engine.ts` / `transformersjs-engine.ts` / `mediapipe-engine.ts`. Same reason — that's a tune/fix candidate for after the baseline.

**Testing:**
- Add unit tests in the existing Vitest suite (find the evalRunner test file under `src/utils/` or `src/__tests__/`) covering:
  - A response starting with `"It sounds like that was hard. What do you mean?"` with `mustNotStartWithBanned: true` → fails with the expected failure message.
  - A response starting with `"Losing the promotion stung. What part hurts most?"` with the same criterion → passes.
  - Match is case-insensitive.
  - Match only counts when the banned stem is at the start (within the first 60 chars), not buried mid-paragraph.
- `npm run build` must pass (`specificity` added to the union must not break existing exhaustive switches — fix any that arise).
- `npm run test` — full suite must remain green (917+ tests; today should grow it by ~4–6).
