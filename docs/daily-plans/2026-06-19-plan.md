## A. Today's objective

Run the C1 conversation-script harness against the **real Gemma 4 E2B** model for
the first time and add **trim instrumentation**, so we get the first hard data on
whether 4096-token context + prior-turn entity surfacing actually holds across a
real 10–20-turn session — measuring entity-retention probe pass-rate, guided-mode
step coherence, *and* exactly when/what `buildManagedMessages` trims at the 4096
boundary. (Roadmap **C2**; closes the measurement half of Fundamental Problem #2,
which was declared "FIXED at 3-turn scale only.")

## B. Why this matters

Yesterday we built the instrument but ran it with a **mock** model. We still do not
know what happens to a real conversation at length. The two questions that matter
to a user who journals for ten minutes:

1. **Does the model still remember the thing I told it ten turns ago?** Problem #2
   was "fixed" only at 3-turn scale; the residual-risk note in
   [ROADMAP.md:12](../ROADMAP.md#L12) is explicit that long-conversation behavior
   is **unmeasured**.
2. **When the conversation gets long enough to overflow 4096 tokens, what silently
   disappears — and does the prior-turn recap save the entity that got trimmed
   out?** Today the driver accumulates **raw** history and never calls
   `buildManagedMessages`, so it does not even mirror what the real app does on the
   send path. We are measuring a path the user never actually hits.

This is the difference between "we think context management works" and "we measured
that the entity from turn 2 survives to turn 18 with a 41% / 100% / … probe
pass-rate under each strategy." C3 (the fixes) is explicitly **gated on this data**
([ROADMAP.md:53](../ROADMAP.md#L53)) — without C2 we cannot justify any
context-limit change.

## C. Current state assessment

**The driver does raw accumulation, not the app's managed path.**
[`conversationDriver.ts:77-81`](../../src/utils/conversationDriver.ts#L77) builds:

```ts
const messages = [
  { role: "system", content: opts.systemInstruction },
  ...history,                      // FULL untrimmed history
  { role: "user", content: turn.user },
];
```

It deliberately does **not** call `buildManagedMessages` (comment at
[:84-85](../../src/utils/conversationDriver.ts#L84): "the whole point of C1 is to
measure raw accumulated context"). That was correct for C1. But the real app send
path uses
[`buildManagedMessages`](../../src/utils/tokenEstimator.ts#L103), which (a) prefixes
a `buildPriorTurnRecap` to the latest user turn and (b) trims oldest history to fit
`MODEL_CONTEXT_LIMIT - RESERVED_FOR_GENERATION - systemTokens - entryTokens`
([tokenEstimator.ts:115-120](../../src/utils/tokenEstimator.ts#L115)). With
`MODEL_CONTEXT_LIMIT = 4096`, `RESERVED_FOR_GENERATION = 384`,
`RESERVED_FOR_SYSTEM = 600`, the history budget is ~3112 tokens
(`AVAILABLE_FOR_HISTORY`, [tokenEstimator.ts:24](../../src/utils/tokenEstimator.ts#L24)).

**The runner is ready and proven headless.** [`scripts/run-eval.ts`](../../scripts/run-eval.ts)
already has the `--scripts` flag wired ([:75](../../scripts/run-eval.ts#L75),
[:186-204](../../scripts/run-eval.ts#L186)) and `eval:scripts` exists in
`package.json`. The Node `onnxruntime-node` CPU path has produced live eval output
on every day from 2026-06-02 through 2026-06-13 (see `docs/eval-runs/*/summary.json`),
so the historical WebGPU/WebLLM headless blocker does **not** apply here.

**Will the current scripts even cross 4096?** Probably not. The longest script
(`script-freewrite-retention`, ~12 turns) at ≤200 generated tokens/reply
(`GEN_DEFAULTS.max_new_tokens`, [run-eval.ts:48](../../scripts/run-eval.ts#L48)) is
~2.5k tokens of history — under the ~3112 budget. **If nothing trims, the trim
instrumentation measures nothing.** So C2 must add at least one script long enough
to force a trim, with the entity established at turn 1–2 and probed *after* the trim
point. This is the experiment that actually has teeth.

**Freeze posture (must preserve):** the standing gate
`git diff origin/main -- src/utils/evalRunner.ts src/utils/evalScorer.ts src/prompts/`
must stay **empty**. All C2 changes land in the **new** files
(`conversationDriver.ts`, `conversationScripts.ts`) + `run-eval.ts`, importing
`buildManagedMessages`/`trimConversationHistory`/`buildPriorTurnRecap` by name
only. No edits to `tokenEstimator.ts`, `conversationContext.ts`, any prompt, or any
safety surface.

### Priority 1 — Trim instrumentation + managed-context mode (`src/utils/conversationDriver.ts`)

**1a. Add a context-strategy option.** Extend `ConversationRunOptions`:

```ts
export type ContextStrategy =
  | "raw"            // current behavior: system + full history + user (C1 default)
  | "managed"        // mirrors the real app: buildManagedMessages (recap + trim)
  | "managed-norecap"; // trim only, NO prior-turn recap (isolates the recap's effect)

export interface ConversationRunOptions {
  systemInstruction: string;
  generate: (messages: { role: string; content: string }[]) => Promise<string>;
  signal?: AbortSignal;
  strategy?: ContextStrategy; // default "raw" so existing tests/behavior are unchanged
}
```

**1b. Build messages per strategy** (replace the single `messages = [...]` block at
[:77-81](../../src/utils/conversationDriver.ts#L77)). Import from `tokenEstimator`
and `conversationContext`:

```ts
import { buildManagedMessages, trimConversationHistory, estimateTokens,
         AVAILABLE_FOR_HISTORY } from "./tokenEstimator";
import { buildPriorTurnRecap } from "./conversationContext";
```

- `"raw"`: unchanged — `[system, ...history, {user}]`.
- `"managed"`: `const { messages, trimResult } = buildManagedMessages(systemInstruction, turn.user, history);`
  (this is the **exact** app send path — recap + trim).
- `"managed-norecap"`: replicate `buildManagedMessages` minus the recap:
  `const tr = trimConversationHistory(history, AVAILABLE_FOR_HISTORY); messages = [system, ...tr.messages, {user: turn.user}];`
  (Do **not** add a recap-suppression flag to `buildManagedMessages` — that would
  edit a frozen-adjacent util's surface. Replicate it locally in the new file
  instead, and add a test asserting the two paths agree when no trim occurs.)

> Note the budget subtlety: `buildManagedMessages` computes its history budget from
> the **system + entry** tokens, while a bare `trimConversationHistory(history,
> AVAILABLE_FOR_HISTORY)` uses the fixed slack. Keep `managed-norecap` faithful to
> `buildManagedMessages`'s budget math (subtract system + entry tokens) so the only
> difference between `managed` and `managed-norecap` is the recap, not the budget.
> Document this inline.

**1c. Per-turn trim telemetry.** Extend `TurnResult` with an optional `context`
block (only populated for non-raw strategies, or for all — your call, but keep
`raw`'s shape backward-compatible so existing tests pass):

```ts
export interface TurnContextInfo {
  strategy: ContextStrategy;
  estHistoryTokens: number;   // estimateTokens over the history fed this turn
  trimmed: boolean;
  droppedTurns: number;       // originalCount - keptCount from the TrimResult
  recapPresent: boolean;      // true if a buildPriorTurnRecap was prepended
  /** For probe turns: was the entity's ORIGINAL establishing turn still inside
   *  the (possibly trimmed) window fed to the model this turn? */
  probeEntityInWindow?: boolean;
}
```

To compute `probeEntityInWindow`: when `turn.retentionProbe` is set, scan the
**messages actually sent this turn** (post-trim, excluding the recap text) for any
of `retentionProbe.mustContainAny`. If absent from the raw window but the probe
still PASSES, that pass is attributable to the recap (or the model's own earlier
replies that survived) — this is the single most useful correlation in the report.

**1d. Summary additions.** Extend `ScriptResult.summary`:

```ts
firstTrimTurnIndex: number | null;  // first turn where trimmed === true; null if never
probesPassedBeforeTrim: number;
probesPassedAfterTrim: number;
probesAfterTrim: number;            // denominator for the after-trim rate
```

This directly answers "measure probe pass-rate before/after the trim point" from
[ROADMAP.md:52](../ROADMAP.md#L52).

**1e. Markdown report.** Extend `scriptReportToMarkdown` to add a column for
`first-trim turn` and a small per-script "context telemetry" table (turn → est
tokens, trimmed?, dropped, recap?, probe-in-window?). Keep the 300-char truncation
style.

### Priority 2 — Boundary-crossing script + live run

**2a. Add `script-freewrite-longtrim` to `src/utils/conversationScripts.ts`**
(mode `freewrite`, ~18–20 turns):
- Turns 1–2 establish a **concrete, single** entity ("My sister **Maya** and I
  stopped speaking after our dad's **birthday dinner**.") — same entity family as
  the existing retention script so probe keywords are reusable.
- Turns 3–16 are ordinary, *substantive* journaling turns (a few sentences each, so
  history actually grows toward the budget). Mix a couple of `expect` turns
  (warmth / no-banned-opener / `maxSentences`) for signal, but most are
  context-only padding.
- Turns ~17 and ~19 are **retention probes** placed *after* the expected trim
  point: `retentionProbe: { entity: "Maya", mustContainAny: ["maya","sister","dinner","birthday"] }`.
- **Verify it crosses the boundary deterministically in a test** (not just at
  runtime): a `conversationScripts.test.ts` case that sums `estimateTokens` over the
  script's user turns + an assumed ~200-token reply per turn and asserts the running
  total exceeds `AVAILABLE_FOR_HISTORY` before the first probe. If it doesn't,
  lengthen the script. (This guards against the script silently never trimming.)

> Do not bloat with filler lorem — keep turns realistic journaling content so the
> measured retention is meaningful. Crisis/harm content stays **out** (C2 is a
> capability/measurement build; safety in long conversations routes through the
> untouched `crisisDetection`/guardrails, never faked in a script).

**2b. Run the three strategies live.** Two acceptable approaches — pick the simpler
to implement cleanly:
- **Preferred:** add a `--strategy=raw|managed|managed-norecap` arg to
  `run-eval.ts` (default `managed`, since that is the real app path), and a
  `--strategy=all` that runs each script under all three and writes a combined
  report. The A/B across strategies is the entire point of C2, so `all` should be
  the documented C2 invocation.
- Acceptable fallback: loop all three strategies unconditionally when `--scripts`
  is passed.

Command for the live C2 run: `npm run eval -- --scripts --strategy=all`
(add an `eval:scripts:all` alias if helpful).

**2c. Execute the live run.**
1. **Smoke first:** `npm run eval -- --scripts --strategy=managed --limit=1` or run
   a single short script to confirm the Node model loads in this slot before
   committing to the full ~20-turn × 3-strategy run (which is many generations and
   slow on CPU).
2. If the model loads, run the full `--strategy=all` and capture
   `docs/eval-runs/<date>/conversation-scripts.md` + the `scripts` block in
   `summary.json`.
3. **If the model genuinely fails to load** (download/onnxruntime error, as on the
   historical browser-blocked days): do **not** fake numbers. Ship the
   instrumentation code + the boundary-crossing script + tests (all mock-proven),
   record the live-run blocker in the change doc and decisions log exactly like the
   2026-05-29/30 entries did, and mark C2 as "instrumented; live run carried over."
   The code half still lands.

### Priority 3 — Findings write-up

Write `docs/eval-runs/<date>/C2-findings.md` (and a 4–6 line summary in the change
doc) interpreting:
- Probe pass-rate per strategy (raw vs managed vs managed-norecap). The key contrast:
  does `raw` (full history) pass probes that `managed-norecap` (trimmed, no recap)
  fails — i.e. is the *trim* what loses the entity? And does `managed` (recap)
  recover those — i.e. does the recap actually do its job at length?
- Step-coherence for the thoughtrecord script under `managed` (the real path).
- `firstTrimTurnIndex` and before/after-trim probe rates.
- **An explicit C3 recommendation**, gated on the data:
  - If `managed` holds probes ≈ `raw` → 4096 + recap is sufficient; C3 may be a
    no-op or a small `RESERVED_FOR_GENERATION` tune. Record that.
  - If `managed` drops probes after the trim point → C3 is justified
    (summarize-trimmed-turns into the recap, per [ROADMAP.md:53](../ROADMAP.md#L53)).
  Whatever the result, state it as a falsifiable claim with the numbers behind it.
