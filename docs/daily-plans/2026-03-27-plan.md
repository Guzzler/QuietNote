# QuietNote Daily Plan — 2026-03-27

## A. Today's Objective

Fix the remaining AnimatePresence exit bugs that prevent closing the PromptSelector and PrivacyDashboard, and fix the silent input loss when sending a message while the model fails to load.

## B. Why This Matters

During live testing today, three concrete bugs were observed:
1. The **PromptSelector dropdown stays open permanently** after clicking Close — it never unmounts from the DOM, remaining visible and overlapping other UI.
2. The **PrivacyDashboard modal stays open permanently** after clicking X — same AnimatePresence pattern, confirmed stuck in DOM.
3. The **user's journal entry is silently lost** when they click Send and the model fails to load. `handleSend` in ChatPanel clears the input immediately via `setUserInput("")`, but the async `newSession` function's null-return path (model load failure) doesn't restore it. Only the catch block does. For a mental health app, losing a user's vulnerable journal entry is unacceptable.

These are the three most visible bugs a user would hit right now. All other features (error banner, mood tracker, sessions) work correctly thanks to prior fixes.

## C. Top 3 Priorities for Today

1. **Fix PromptSelector AnimatePresence exit bug** — The dropdown never unmounts after clicking Close. Confirmed during live testing. Same root cause as the MoodTracker (03-25) and CrisisResources (03-26) fixes.

2. **Fix PrivacyDashboard AnimatePresence exit bug** — The modal never unmounts after clicking X or Close. Confirmed during live testing. Same root cause and same fix pattern.

3. **Fix input loss when model fails to load** — `handleSend` clears the textarea immediately, but the async `newSession`/`replyInThread` functions only restore input in the `catch` block, not in the `if (!e) return` path. Move `setUserInput("")` into the success callback or add input restoration to the null-return path.

## D. Concrete Implementation Plan

### Priority 1: Fix PromptSelector AnimatePresence Exit

**Root cause:** `PromptSelector.tsx` uses `<AnimatePresence>{isOpen && (<motion.div>...</motion.div>)}</AnimatePresence>` for the dropdown. Framer Motion v12 doesn't properly unmount children with this conditional pattern when `isOpen` becomes false — the exit animation never completes and the DOM node persists.

**Exact changes to `src/components/PromptSelector.tsx`:**
- Replace `<AnimatePresence>{isOpen && (<motion.div>...</motion.div>)}</AnimatePresence>` with `{isOpen && (<div>...</div>)}`
- Change the outer `motion.div` to a plain `div` (keep all styling)
- Keep the inner `<AnimatePresence mode="wait">` for prompt content transitions (this one works because it animates between keyed children, not conditional presence)
- Remove unused `AnimatePresence` from the framer-motion import if the outer one was the only usage

**Where it lives:** `src/components/PromptSelector.tsx`

**How to test:**
1. Click "Prompt" button — dropdown opens upward
2. Click "Close" — dropdown disappears from DOM
3. Click "Prompt" again — dropdown re-opens with a new prompt
4. Click "Use This" — prompt text fills textarea and dropdown closes
5. Verify dropdown is NOT visible behind other modals when closed

**What could go wrong:** Removing the outer AnimatePresence loses the dropdown open/close animation. This is the same trade-off accepted for MoodTracker and CrisisResources — working close button is more important than entry/exit animation.

### Priority 2: Fix PrivacyDashboard AnimatePresence Exit

**Root cause:** `PrivacyDashboard.tsx` uses `<AnimatePresence>{isOpen && (<>...<motion.div/>...<motion.div/>...</>)}</AnimatePresence>` — the exact same broken pattern as MoodTracker and CrisisResources. The fragment wrapper (`<>...</>`) combined with AnimatePresence and conditional rendering prevents proper unmounting.

**Exact changes to `src/components/PrivacyDashboard.tsx`:**
- Replace the outer `<AnimatePresence>{isOpen && (<>...</>)}</AnimatePresence>` with `if (!isOpen) return null` at the top of the component
- Change backdrop `motion.div` to plain `div`
- Change modal wrapper `motion.div` to plain `div`
- Add `onClick={onClose}` on the backdrop div for click-outside-to-close (if not already present)
- Add `onClick={(e) => e.stopPropagation()}` on the inner content container
- Keep the inner `<AnimatePresence>` for the delete confirmation toggle (this one works — it animates between states, not conditional presence)
- Remove `motion` from the framer-motion import if no longer used for the outer elements

**Where it lives:** `src/components/PrivacyDashboard.tsx`

**How to test:**
1. Click "Privacy" button — dashboard opens
2. Click X button — dashboard disappears from DOM
3. Re-open, click "Close" button — dashboard disappears
4. Verify dashboard is NOT stuck behind other UI elements when closed
5. Verify delete confirmation still animates when toggled

**What could go wrong:** Same trade-off — no entry/exit animation. The inner delete confirmation animation should still work since it uses a different AnimatePresence scope.

### Priority 3: Fix Input Loss on Model Load Failure

**Root cause:** In `ChatPanel.tsx` line 243, `setUserInput("")` runs synchronously after calling the async `newSession(text)`. Since `newSession` is not awaited, the input is cleared immediately. If `loadModel()` returns null (model failed to load), the `if (!e) return` path in `newSession` (App.tsx line 158-161) does NOT restore the user's input. Only the `catch` block (line 288) restores it. The input is silently lost.

**Exact changes to `src/components/ChatPanel.tsx`:**
- Remove `setUserInput("")` from after the `newSession`/`replyInThread` calls
- Instead, pass a `clearInput` callback (or simply have `newSession`/`replyInThread` call `setUserInput("")` in their success paths)
- Simpler approach: make `handleSend` async, await the result, and only clear on success

**Alternative (simpler, fewer changes across files):**
- In `src/App.tsx`, add `setUserInput(firstMessage)` to the `if (!e) return` path in `newSession` (line 160)
- Same for `replyInThread` `if (!e) return` path (line 326)
- This ensures input is always restored when the model fails to load, matching the catch block behavior

**Where it lives:** `src/App.tsx` (preferred) or `src/components/ChatPanel.tsx`

**How to test:**
1. With model in error state, type a journal entry and click Send
2. Verify the text remains in the textarea after the model fails to load
3. Verify no brief "flash" where the text disappears then reappears
4. Verify that on successful send (when model works), the input IS cleared normally

**What could go wrong:** The simpler approach (restore in null path) still has a brief flash where input disappears and reappears. The cleaner approach (don't clear until success) requires making `handleSend` async or restructuring the callback.

## F. UX & Design Review

### How the app feels as a product:
The app's core infrastructure is solid — error handling (03-26), mood tracker (03-25), and crisis resources (03-26) all work correctly now. But the "close" interaction is broken for 2 of 5 major UI panels (PromptSelector, PrivacyDashboard), making them feel stuck. Once opened, these panels persist in the DOM, overlapping each other. This creates a "nothing closes" feeling that undermines the polished shell.

### What a first-time user would think:
1. "App loaded, error message is clear, I'll try again later" — good ✅
2. "Let me check the privacy features..." → opens dashboard → clicks X → "Wait, it's still there?"
3. "Let me try a prompt" → opens prompt selector → clicks Close → "Why is this still showing?"
4. The user now has both the Privacy Dashboard AND the Prompt Selector stuck on screen simultaneously.

### Biggest UX gap right now:
**Modal/dropdown close reliability.** Two of the five major panels can't be dismissed. This is the most visible and frustrating bug for any user who explores the app's features. The fix is well-established (same pattern applied successfully to MoodTracker and CrisisResources).
