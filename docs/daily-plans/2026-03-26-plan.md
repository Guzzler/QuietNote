# QuietNote Daily Plan — 2026-03-26

## A. Today's Objective

Fix silent failure when the model fails to load and fix the CrisisResources modal close bug — the two most impactful reliability issues a user would hit today.

## B. Why This Matters

During live testing, sending a journal entry produced **zero feedback** — no loading indicator, no error message, no session created. The user's message simply vanished. This is catastrophic UX: a user pouring out their feelings gets nothing back and has no idea why. Separately, the CrisisResources modal has the same AnimatePresence close bug that was fixed in MoodTracker on 03-25 — if a user in crisis can't close the resources modal, they're trapped in a distressing UI state.

## C. Top 3 Priorities for Today

1. **Add error handling and user feedback when model loading fails** — When `loadModel()` fails or returns null, the user currently gets no feedback and their message is silently lost. Add proper error state, retry UI, and preserve the user's message on failure.

2. **Fix CrisisResources modal close button (same AnimatePresence bug as MoodTracker)** — The CrisisResources component still uses the `AnimatePresence` + `{isOpen && <><motion.div/>...}` fragment pattern that was broken in MoodTracker. Apply the same fix: replace with conditional rendering and plain divs.

3. **Fix Prompt button click area overlap with Send button** — During testing, clicking the send button area sometimes triggered the Prompt selector panel instead. The Prompt button's click target appears to overlap the send button region. This makes the core interaction (typing + sending) unreliable.

## D. Concrete Implementation Plan

### Priority 1: Error Handling for Model Load Failure

**Root cause:** `useMLCEngine.ts` `loadModel()` has a `try/finally` but no `catch` block. When `CreateMLCEngine` throws (e.g., WebGPU available but WASM compilation fails, network timeout during model download, out of memory), the error becomes an unhandled promise rejection. In `App.tsx`, `newSession()` calls `const e = await loadModel()` — if it returns `null` (WebGPU unsupported) or throws, the code proceeds to call methods on a null/undefined engine, or the session is created but never populated. The user's input was already cleared by `handleSend()`.

**Exact changes:**

- In `src/hooks/useMLCEngine.ts`:
  - Add an `error` state: `const [error, setError] = useState<string | null>(null)`
  - Add a `catch` block in `loadModel()` that sets the error state with a user-friendly message
  - Return `error` and a `clearError` function from the hook

- In `src/App.tsx`:
  - Destructure `error` from `useMLCEngine()`
  - In `newSession()`: check if `e` is null/undefined after `await loadModel()` — if so, show an error and return early **before** clearing the user's input
  - In `replyInThread()`: same null check for `e` at line 309
  - Add `catch` blocks to both `newSession` and `replyInThread` that set a visible error state instead of silently failing

- In `src/components/ChatPanel.tsx`:
  - Move `setUserInput("")` into `handleSend` only AFTER confirming the session was created, OR pass the text back to the input on failure
  - Alternative (simpler): keep the current `setUserInput("")` but add an `errorMessage` prop that shows a toast/banner when an error occurs

**Where it lives:** `src/hooks/useMLCEngine.ts`, `src/App.tsx`, `src/components/ChatPanel.tsx`

**Dependencies:** None

**How to test:**
1. Open the app in a browser where WebGPU is available but the model hasn't been cached
2. Send a message while the model is still downloading — verify a loading indicator appears
3. If model download fails (simulate by going offline mid-download), verify an error message appears
4. Verify the user's original message is preserved or shown in the error state
5. Verify a "Retry" option is available

**What could go wrong:**
- The error message might be too technical (WebLLM error strings). Need to map to user-friendly messages.
- The loading state interaction between `loading` (from hook) and `busy` (from App) needs careful coordination.

### Priority 2: Fix CrisisResources Modal Close

**Root cause:** Same as MoodTracker — Framer Motion v12 `AnimatePresence` with conditional fragments (`{isOpen && <><motion.div/><motion.div/></>}`) doesn't properly unmount children when `isOpen` toggles to false.

**Exact changes to `src/components/CrisisResources.tsx`:**
- Replace `<AnimatePresence>{isOpen && (<>...</>)}</AnimatePresence>` with `if (!isOpen) return null` at the top of the component
- Change backdrop `motion.div` to plain `div` (keep the styling)
- Change modal wrapper `motion.div` to plain `div`
- Add `onClick={onClose}` on the modal wrapper div (the `fixed inset-0 z-50` one)
- Add `onClick={(e) => e.stopPropagation()}` on the inner content div to prevent close when clicking inside

**Where it lives:** `src/components/CrisisResources.tsx`

**How to test:**
1. Trigger crisis detection by sending a message with crisis keywords
2. Verify the CrisisResources modal opens
3. Click X button — verify modal closes
4. Re-open, click outside the modal — verify it closes
5. Click inside the modal — verify it does NOT close

**What could go wrong:** Removing entry animation means the crisis modal appears instantly. For a safety-critical modal, this is actually fine — immediacy is more appropriate than a smooth slide-in when someone is in distress.

### Priority 3: Fix Prompt Button Click Area Overlap

**Root cause hypothesis:** The Prompt button and the Send button are in the same flex container. The Prompt button's click target (or its parent element's event zone) may extend into the send button area. This was observed during testing: clicking what appeared to be the send button region triggered the Prompt selector.

**Exact changes to `src/components/ChatPanel.tsx`:**
- Inspect the layout of the Prompt button and send button container (lines ~377-397)
- Add explicit `z-index` or `position: relative` to ensure the send button is above the Prompt panel trigger area
- If the Prompt button's parent div extends too far, constrain its width with `w-auto` or `flex-shrink-0`
- Add `e.stopPropagation()` to the send button's onClick to prevent event bubbling

**Where it lives:** `src/components/ChatPanel.tsx`

**How to test:**
1. Type a message in the textarea
2. Click the send button — verify the message sends (not the Prompt panel opening)
3. Click the Prompt button — verify the Prompt panel opens
4. Verify there's no overlap region where both activate

**What could go wrong:** The overlap might be caused by the Prompt dropdown positioning, not the button itself. May need to adjust the dropdown's absolute positioning.

## F. UX & Design Review

### How the app feels as a product:
The shell is solid — the layout is clean, the mood tracker now works properly, the privacy dashboard builds trust, and the journal prompts are helpful. But the core interaction (send a message, get a response) is completely broken in this test environment. More importantly, even when the model fails, the user gets **zero feedback**. No loading spinner, no error message, no "the model is downloading" state. Just silence.

### What a first-time user would think:
1. "Nice looking app, clean design"
2. "Let me write about my day..." → types message → clicks send
3. "...where did my message go? Did it send? Is it loading?"
4. "Nothing happened. Is the app broken?"
5. Closes the app.

### Biggest UX gap right now:
**Error handling and loading feedback.** The 03-25 model switch was the right move for response quality, but the app has no resilience when the model fails to load. A user on a slow connection who has to wait for 1+ GB model download needs clear feedback. A user whose browser doesn't support the WASM compilation needs a clear error. The message being silently eaten is the worst possible outcome.

### Secondary UX gaps:
- Prompt button click area overlap makes the send button unreliable
- CrisisResources modal can't be closed (same AnimatePresence bug)
