## A. Today's objective

Close the one failing cluster the fresh input-robustness baseline surfaced: **Family 2 — gibberish / punctuation-only input**, where the model projects an emotional read instead of plainly asking what the user meant. Fix it via the proven mechanism ladder (prompt-tune first → deterministic guard only if the prompt layer is exhausted). This is Track **B2** in [docs/ROADMAP.md](../ROADMAP.md), and it is the named NEXT item.

## B. Why this matters

22% of real launched-app entries are ≤5 words and the corpus contains genuine gibberish, greetings-as-entries, and stray-keystroke entries (see [field-notes/2026-06-09-real-user-data-plan.md](../field-notes/2026-06-09-real-user-data-plan.md)). When a user fat-fingers `asdkfj` or types `.......` while gathering their thoughts, the worst response is one that **invents a feeling they never expressed** — *"You typed '.......', which leaves space for many things to surface. When you pause like that, what emotion surfaces…"*. That is the journal telling the user how they feel based on noise. It erodes trust faster than a bland reply. The right behavior is humble and plain: *"I didn't quite catch that — what's on your mind?"* B1 proved the criterion is reachable (freewrite `ir-2.1` already passes with exactly that shape); the model is just **inconsistent**, especially in the three guided modes. B2 makes it consistent.

### The eval cases (the gate — DO NOT edit without a freeze-lift)

[src/utils/evalRunner.ts:1213-1268](../../src/utils/evalRunner.ts) — `ir-2.1` and `ir-2.2`. Pass requires:
- `mustContainAny`: a plain-clarify phrase — `"didn't quite"`, `"could you"`, `"tell me more"`, `"not sure i"`, `"say more"`, `"what's on"` (ir-2.2 also allows `"when you're ready"`, `"here when"`).
- `mustNotContainAny`: emotion-projection phrases — `"sounds like you"`, `"tough time"`, `"struggling"`, `"overwhelmed"`, `"i hear that you're"`.
- `mustNotStartWithBanned: true`, `maxSentences: 4`.

**The current failures are mostly on the `mustContainAny` side**: the model asks *a* question but not a *plain-clarify* one (it asks "what emotion surfaces", "what thoughts led to typing them"). The `mustNotContainAny` emotion-read guard mostly held. So the fix is to make the model **plainly ask for clarification** on unintelligible input rather than interpreting it.

### The conflicting rule (root cause — must be addressed)

Every prompt opens with the **FIRST LINE RULE**: *"open by naming something concrete the user wrote… If you cannot find a concrete detail to name, restate one of their own phrases back to them."* For `.......` or `asdkfj` **there is no concrete detail and no phrase to restate**. The model, dutifully following this rule, manufactures a "concrete" reading of the noise — which is exactly the projection failure. **The clarify beat must be written as an explicit exception to the FIRST LINE RULE**, or the two rules will keep fighting.

Prompt file: [src/prompts/systemPrompts.ts](../../src/prompts/systemPrompts.ts) (210 lines, 5 exported instructions: `SYSTEM_INSTRUCTION` freewrite L12, `GRATITUDE_SYSTEM_INSTRUCTION` L64, `CHECKIN_MORNING_INSTRUCTION` L97, `CHECKIN_EVENING_INSTRUCTION` L121, `THOUGHT_RECORD_INSTRUCTION` L147). Each already carries a `FIRST LINE RULE` and a `Continuity` line — same insertion pattern Day-3 and Day-9 used for tunes.

### Mechanism-B substrate already exists

[src/utils/responseShaping.ts](../../src/utils/responseShaping.ts) already implements the "detect a bad response shape → one re-prompt retry" pattern (`isBareDeflection`, `DEFLECTION_REPROMPT_INSTRUCTION`, `withDeflectionReprompt`), wired DRY into both the eval path (`scripts/run-eval.ts`) and both App.tsx send paths. If the prompt layer is exhausted, B2's fallback extends this exact pattern — no new architecture.

## E. Concrete implementation plan

### Priority 1 — Mechanism A: prompt beat (try this first, alone)

**File:** [src/prompts/systemPrompts.ts](../../src/prompts/systemPrompts.ts) — add the *same* beat to all 5 instructions, placed immediately after each prompt's FIRST LINE RULE block so it reads as a scoped exception.

**Suggested text (tune as needed — keep it short, plain, and non-emotional):**

> **UNINTELLIGIBLE INPUT RULE (exception to the FIRST LINE RULE):** If the user's message is gibberish, random characters, or only punctuation/whitespace with no discernible words or meaning, do NOT guess at or name any emotion, and do NOT invent a "concrete detail" from the noise. Plainly say you didn't quite catch that and gently invite them to share what's on their mind. Example: "I didn't quite catch that — what's on your mind right now?" or "I'm not sure I caught that. Could you tell me more about what you wanted to share?"

Design notes the executor must honor:
- **Use the scorer's accepted clarify phrasings** so a genuinely-good body actually passes: the examples deliberately contain `"didn't quite"`, `"could you"`, and `"tell me more"` (all in `mustContainAny`). Do **not** invent novel phrasings the gate won't recognize — that would force a scorer edit (see the freeze note below).
- **Avoid the banned emotion-read phrases** in the examples (`"sounds like you"`, `"struggling"`, `"overwhelmed"`, `"i hear that you're"`, `"tough time"`).
- **Guided-mode wording:** in gratitude/checkin/thoughtrecord, the rule must take precedence over the mode flow for that turn (don't ask "what are you grateful for" in response to `.......`). Mirror how the SAFETY CARVEOUT is scoped ("set the flow aside for this turn"). It must NOT touch or weaken the SAFETY CARVEOUT itself — gibberish is not a crisis signal; the two rules are independent.
- **Keep `maxSentences: 4`** — the clarify reply should be 1–2 sentences, not a paragraph.

**Verify (gate decision):**
```
npm run eval -- --dimensions=input_robustness   # all 4 modes, full 12-case dimension
```
**SHIP-A iff** `ir-2.1` AND `ir-2.2` PASS in **≥3/4 modes each** with genuine plain-clarify bodies (read the actual bodies, not just the tally — confirm they ask for clarification and name no emotion), AND no Family 1/3/4/5 case regresses (they were all 4/4 — protect them). If A clears this bar, **stop here**; do not build mechanism B.

### Priority 2 — Mechanism B: deterministic guard (ONLY if A is exhausted, same session)

Pivot to B in the same session if, after a reasonable prompt iteration, `ir-2.*` still fails in ≥2 modes. Follow the Day-9 mechanism-B pattern exactly.

**File:** extend [src/utils/responseShaping.ts](../../src/utils/responseShaping.ts):
- `isUnintelligibleInput(userText: string): boolean` — true when the latest user message has no alphanumeric word of length ≥2 after stripping punctuation/whitespace, OR is entirely punctuation/whitespace, OR is only random-consonant runs with no vowels above a short length. Keep it **conservative** — false positives on real terse entries (`"ok"`, `"meh"`, `"ugh"`, `"idk"`) are unacceptable; those are valid Family-1 inputs that already pass. Unit-test the boundary cases.
- Either (a) `UNINTELLIGIBLE_REPROMPT_INSTRUCTION` + a `withUnintelligibleReprompt` re-prompt (preferred — keeps the model's voice), or (b) a deterministic clarify substitution string if the re-prompt still projects. Prefer (a); fall back to (b) only if (a) is unreliable.
- Wire DRY into the eval generate path (`scripts/run-eval.ts`) and **both** App.tsx send paths, identically to `withDeflectionReprompt`. The guard must run **after** `crisisDetection`/`responseGuardrails`, never bypassing them, and must be **suppressed when the input is a crisis signal** (it won't be — gibberish isn't crisis — but compose the predicates so a crisis turn always wins).

**Verify:** same input_robustness re-run; plus targeted sampling of the substituted/re-prompted bodies.
