## B. Why this matters

The genuinely valuable on-device tool is `search_past_entries` ("when did I last write about my sister?") — it turns a flat chat into something that remembers your journal. But the 2026-03-12 design ([`design/tool-calling-architecture.md`](../design/tool-calling-architecture.md)) deliberately chose **client-side keyword extraction over model-side tool calling** because Gemma 2 2B couldn't be trusted with structured output. Two things changed since: the canonical eval model is now Gemma 4 E2B, and Days 8–9 built the exact machinery a tool loop needs (deterministic response-shape detection + one-shot re-prompt — `responseShaping.ts`). D1 re-tests that decision **cheaply and measurably**, and is explicitly allowed to kill the track.

The real-user cost of getting this wrong is high: a journal that randomly emits `<<tool:…>>` syntax in a tender moment is *worse* than no tools. So the spike's headline metric is not "can it call tools" but **"does it stay silent when it should"** (false-call rate on ordinary journaling turns must be ~0).

## E. Concrete implementation plan

### Priority 1 — Grammar + parser (`src/utils/toolCalls.ts`, NEW file)

**Grammar (one line, NOT free JSON):**
```
<<tool:NAME arg=value arg=value>>
```
- Emitted on its **own line**, nothing else on that line.
- `NAME` ∈ a fixed allow-list. Args are `key=value`, space-separated, values are single tokens or `quoted strings`.

**Three tools (from the design doc's Tier-1/Tier-2 list — all user-confirmed via cards in the eventual D2 build, never auto-executed):**

| Tool | Args | Arg domain |
|---|---|---|
| `suggest_prompt` | `category` | one of the 8 real `PromptCategory` values from `journalPrompts.ts` (import the list — do not hardcode a divergent set) |
| `search_past_entries` | `query` | free-text quoted string (the keyword/topic to search journal history for) |
| `log_mood` | `emotion`, `intensity` | `emotion` ∈ the 10 `MoodEmotion` values from `types.ts`; `intensity` ∈ 1–10 integer |

**Exports (pure, no React, no storage):**
```ts
export const TOOL_GRAMMAR_INSTRUCTION: string; // the prompt beat that teaches the grammar (see below)
export interface ParsedToolCall { name: string; args: Record<string,string>; raw: string; }
export interface ToolParseResult {
  calls: ParsedToolCall[];        // syntactically well-formed calls found
  validCalls: ParsedToolCall[];   // calls that also pass name+arg validation
  invalidCalls: ParsedToolCall[]; // well-formed shape but bad name/arg (→ retry candidates)
  strippedText: string;           // response with all tool-call lines removed (display text)
}
export function parseToolCalls(response: string): ToolParseResult;
export function validateToolCall(call: ParsedToolCall): { valid: boolean; reason?: string };
export const TOOL_REPROMPT_INSTRUCTION: string; // mirrors DEFLECTION_REPROMPT_INSTRUCTION
```
- `parseToolCalls` uses a strict regex for the `<<tool:…>>` line, splits args, then runs `validateToolCall` on each to bucket valid/invalid.
- `validateToolCall`: name in allow-list; required args present; arg values in their domain (import `PromptCategory` set + `MoodEmotion` set; intensity parse+range-check). Unknown args → invalid.
- `strippedText` is what would render to the user — proves the syntax never leaks into display text (critical for the journaling-tone risk).

**`TOOL_GRAMMAR_INSTRUCTION`** — the prompt beat injected ONLY in the eval runner (see Priority 2), never in `systemPrompts.ts`. Must include: the exact one-line grammar, the three tools + their args, **and an explicit "most turns need NO tool — only emit one when clearly useful; never emit tool syntax in ordinary reflection"** clause (this is what the false-call metric tests). Include 1–2 few-shot examples (one tool-warranted turn → call; one ordinary turn → no call).

### Priority 2 — 20-case eval (`src/utils/toolCallEval.ts`, NEW file + `--tools` flag)

**`src/utils/toolCallEval.ts` (NEW, pure data + scorer — does NOT import evalRunner/evalScorer):**
```ts
export interface ToolEvalCase {
  id: string;
  mode: JournalingMode;
  userMessage: string;
  expectCall: boolean;           // true = a tool is warranted; false = ordinary turn, expect silence
  expectedTool?: string;         // when expectCall
  expectedArgs?: Record<string,string>; // for argument-accuracy scoring (allow partial/fuzzy on free-text query)
}
export const TOOL_EVAL_CASES: ToolEvalCase[]; // 20 cases — see split below
export function scoreToolCase(c: ToolEvalCase, parse: ToolParseResult): {
  validCallMade: boolean;        // for expectCall cases: a valid call to expectedTool
  argAccurate: boolean | null;   // null when no call or not expectCall
  falseCall: boolean;            // for !expectCall cases: any tool call emitted at all
};
```

**20-case split (the spike's whole point is the false-call denominator — keep it large):**
- **8 tool-warranted cases** (`expectCall: true`), spread across tools & modes:
  - 3× `suggest_prompt` (e.g. "I don't know what to write about today" → category inferred; vague-anxiety turn; gratitude-mode "help me start").
  - 3× `search_past_entries` (e.g. "when did I last write about my sister?", "have I mentioned my job interview before?", "what did I say about Maya?").
  - 2× `log_mood` (e.g. "I'm feeling really anxious about tomorrow" → emotion=anxious; a clear high-intensity sad turn).
- **12 ordinary-journaling cases** (`expectCall: false`) — the false-call guard. Pull realistic turns from the existing empathy/specificity case bodies and the conversation scripts (ordinary reflection, gratitude lists, check-in narration, a Thought-Record step answer). **At least 2 should be near-misses** that mention prompts/moods/the past in passing but do NOT warrant a tool (e.g. "I felt happy today and I'm grateful for it" — narrating a mood ≠ asking to log one; "I keep thinking about what I wrote yesterday" — reflection, not a search request). These are where false calls hide.

**`run-eval.ts` `--tools` flag (mirror the `--scripts` wiring at `scripts/run-eval.ts:84`):**
- `const RUN_TOOLS = args.includes("--tools");`
- When set, after the per-mode loop, iterate `TOOL_EVAL_CASES`: build messages = `[{role:"system", content: getBaseSystemInstruction(case.mode) + "\n\n" + TOOL_GRAMMAR_INSTRUCTION}, {role:"user", content: case.userMessage}]`. (Augmentation is **string concatenation at runtime in the runner** — `systemPrompts.ts` stays byte-identical, freeze gate held.)
- Generate → `parseToolCalls` → `scoreToolCase`. **Retry rule (the gate counts this):** if `expectCall` and the response has `invalidCalls` but no `validCalls`, append `TOOL_REPROMPT_INSTRUCTION` and regenerate **once**; re-parse; count as valid-with-retry if it now passes.
- Write `docs/eval-runs/<UTC-date>/D1-tool-spike.md` (per-case table: id, mode, expectCall, tool emitted, valid?, arg-accurate?, false-call?, retry-used?) + attach a `tools` block to `summary.json` **only when `--tools` is passed** (keep default `summary.json` shape byte-identical, exactly as `--scripts` does).
- Add `"eval:tools": "tsx scripts/run-eval.ts --tools"` to `package.json`.
