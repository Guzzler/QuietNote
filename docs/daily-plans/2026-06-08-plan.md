## A. Today's objective

Resolve the `empathy-mt-3` prior-turn entity-drop — the 4/4-mode experience-FAIL that survived four independent samples (Days 3–6) and the Day-3 prompt-only continuity directive — by structurally **surfacing prior-turn entities adjacent to the current user turn** instead of leaving them buried in the middle of the chat history. This is the first `feat:` of the BUILD phase (Fundamental Problem 2/3: multi-turn coherence).

## B. Why this matters

Across every sample, when a user types a brief emotional follow-up ("I'm just so tired of everything." / "Yeah.") the model latches the *surface words of the latest turn* and drops the entity established two turns earlier (the family dinner, the hurtful thing said to mom, the shame). The user wrote something vulnerable 90 seconds ago and the model acts like it never happened. That is the single most "tech-demo, not a journal" failure mode left in the product — it breaks the core "feel heard" loop precisely at the most emotionally loaded moment. A static prompt sentence has been proven insufficient three times; the fix has to change *what the model sees near the current turn*, not what we tell it to do.

## E. Concrete implementation plan

### Priority 1 — Prior-turn entity-surfacing util (PRIMARY mechanism: context-summary injection)

This is explicitly the mechanism candidate the EVAL cycle authorized; it is **not** "another system-prompt sentence" (that is a static instruction in `systemPrompts.ts`). This injects **dynamic, per-conversation content** derived from the actual prior turns, positioned next to the current turn.

**New file: `src/utils/conversationContext.ts`**

Export a pure function:
```ts
export interface PriorTurn { role: string; content: string }

/**
 * Builds a compact, single-line recap of the salient entities (named people,
 * events, places) and feelings the USER established in earlier turns of THIS
 * conversation. Returns null when there is nothing worth recapping (0–1 prior
 * user turns, or no extractable anchors).
 *
 * Mechanism: salience injection. The recap is placed adjacent to the current
 * user turn so the model reads the established entity LAST, defeating the
 * surface-word-latch on brief follow-ups ("Yeah.", "I'm just so tired…").
 */
export function buildPriorTurnRecap(history: PriorTurn[]): string | null
```

Implementation guidance (keep it deterministic and testable — no model call):
- Consider only `role === "user"` turns in `history` (assistant turns are the model's own paraphrase; recapping them risks echo loops).
- Require **≥2 prior user turns OR ≥1 prior user turn that is substantively longer than the current** before emitting (avoid recapping a single trivial opener).
- Extract anchors from those user turns:
  - **Named entities / nouns** — capitalized non-sentence-start tokens (mom, Sarah, Miguel… note "mom"/"family dinner" are lowercase, so ALSO match a small curated relationship/relation lexicon: `mom, mum, mother, dad, father, sister, brother, partner, boss, friend, coworker, colleague` and event nouns `dinner, meeting, graduation, layoff, argument, fight, funeral`). Reuse `extractThemes` from `themeExtractor.ts` if it yields cleaner anchors — executor's choice; whichever surfaces "family dinner / mom / shame" for the mt-3 fixture.
  - **Feeling words** — reuse the emotion keyword list already in `App.parseEmotions` / `emotionExtractor.ts` (`ashamed, shame, guilty, tired, exhausted, …`).
- Compose a **single line**, e.g.:
  `Earlier in this conversation they spoke about: the family dinner, saying something hurtful to their mom, and feeling ashamed. Connect your reply to that before responding to their latest message.`
  Cap at ~3 anchors and ~200 chars. Do NOT fabricate anchors not present in the text.

**Wire into the EVAL path — `src/utils/evalDriver.ts:45-49`:**
```ts
const recap = buildPriorTurnRecap(c.priorTurns ?? []);
response = await opts.generate([
  { role: "system", content: opts.systemInstruction },
  ...(c.priorTurns ?? []),
  ...(recap ? [{ role: "user", content: `[continuity] ${recap}` }, { role: "assistant", content: "Understood." }] : []),
  { role: "user", content: c.prompt },
]);
```
> **Template note:** the Gemma chat template alternates user/assistant and merges `system` into the first user turn. Injecting a bare extra `system` mid-conversation can break `apply_chat_template`. The safest, template-agnostic placement is a short synthetic `user`→`assistant` pair carrying the recap, immediately before the real current user turn (shown above). **Alternative placement** (also acceptable, fewer tokens) — prepend the recap to the current user content itself:
> ```ts
> { role: "user", content: recap ? `${recap}\n\n${c.prompt}` : c.prompt }
> ```
> Executor: try the prepend-to-current-user form first (simplest, guarantees adjacency, no template risk). Only fall back to the synthetic-pair form if the model starts answering the bracketed recap instead of the user.

**Wire into the APP path — `src/utils/tokenEstimator.ts:buildManagedMessages`:**
Apply the **same** recap, derived from `conversationHistory`, using the **same placement** chosen above, so real users get the identical behavior the critic measured. Keep the recap OUTSIDE the trim budget accounting only if it's small; simplest is to build the recap from the *untrimmed* history (so the entity survives even when the raw turn gets trimmed — this is a bonus: it preserves salience past the context window) and prepend to `currentEntry` before the existing assembly. Do not alter the trim math otherwise.

**Keep the two call sites DRY:** both import `buildPriorTurnRecap` from the new util. No duplicated extraction logic.
