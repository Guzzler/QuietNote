# Daily Plan — 2026-05-25

## A. Today's Objective

Tackle **Problem 3: Model response quality** by building a runnable, in-browser eval harness that executes the existing eval cases against the *real* loaded model (Gemma 2 2B via WebLLM), captures real responses, and scores them. The current `evalRunner.ts` / `evalScorer.ts` define the cases and scoring logic but have **never been driven by actual model inference** — they're regex heuristics waiting for output that never arrives. Today we wire them up end-to-end behind a dev-only panel and produce a first baseline report.

## B. Why This Matters

Yesterday (2026-05-24) fixed the two blocking UX issues: guided modes now persist as a sticky header during the chat (Problem 1) and the context window was bumped from 2048 → 4096 tokens with multi-turn coverage tests (Problem 2). The core loop *technically works*. But the next thing a real user notices is that responses feel generic, formulaic, and disconnected from what they wrote. We cannot tune the system prompt, temperature, or repetition penalty until we can actually *see* current model behavior on a fixed test set and re-run after each tweak.

Concretely, users keep getting "How does that make you feel?" follow-ups regardless of what they wrote. We need data to:
- Quantify how often the model parrots formulaic questions vs. references specifics from the user's message
- Detect when the persona prompt is being overridden (jailbreak resistance)
- Verify the medical-refusal guidelines actually fire (melatonin example etc.)
- Measure response length distribution against the "3-4 sentences total" target

Without a real eval, every prompt tweak is guesswork.

## E. Concrete Implementation Plan

### Priority 1: `src/utils/evalDriver.ts` (NEW)

Create a new file. Do NOT modify `evalRunner.ts` or `evalScorer.ts` — those are the pure scoring layer.

```ts
// src/utils/evalDriver.ts
import type { EvalCase, EvalResult } from "./evalRunner";
import { EVAL_CASES, evaluateResponse } from "./evalRunner";
import { aggregateResults } from "./evalScorer"; // confirm exported name

export interface EvalRunOptions {
  systemInstruction: string;
  generate: (messages: { role: string; content: string }[]) => Promise<string>;
  dimensions?: EvalDimension[];          // filter; default = all
  onProgress?: (done: number, total: number, last: EvalResult) => void;
  signal?: AbortSignal;
}

export interface EvalRunReport {
  startedAt: string;
  finishedAt: string;
  modelLabel: string;                    // e.g. "webllm/gemma-2-2b-it-q4f16_1"
  systemInstructionHash: string;         // sha-1 of the prompt, for diffing
  results: EvalResult[];
  summary: ReturnType<typeof aggregateResults>;
}

export async function runEvalSuite(opts: EvalRunOptions): Promise<EvalRunReport> {
  const cases = opts.dimensions
    ? EVAL_CASES.filter(c => opts.dimensions!.includes(c.dimension))
    : EVAL_CASES;
  const results: EvalResult[] = [];
  for (let i = 0; i < cases.length; i++) {
    if (opts.signal?.aborted) break;
    const c = cases[i];
    const response = await opts.generate([
      { role: "system", content: opts.systemInstruction },
      { role: "user", content: c.prompt },
    ]);
    const r = evaluateResponse(response, c);
    results.push(r);
    opts.onProgress?.(i + 1, cases.length, r);
  }
  // … assemble report
}
```

Key behaviors:
- One-shot per case (no multi-turn) for now — multi-turn evals come later.
- Wraps each `generate` in a try/catch; on error, record a failed result with `failures: ["inference error: ..."]` and continue. Do not abort the whole run on a single failure.
- Caller supplies the `generate` closure so we don't import the engine here (keeps this file unit-testable with a mock).
