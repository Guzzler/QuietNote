- WebLLM (`@mlc-ai/web-llm`) — WebGPU only; headless Chromium throws `Cache.add UnknownError` (documented across all three reports).

- Transformers.js (`@huggingface/transformers`) — used for the Day-1 report **in a real browser tab**, but the library *also runs in Node.js* and we have never used that path.

The execution task is a scheduled, headless slot. It cannot reliably drive a real Chrome+WebGPU session and babysit a multi-GB model load through a UI. So as long as the **only** way to get model output is the `?eval=1` EvalPanel, the loop will keep being "deferred to the next interactive session" — which never comes, because the next session is another headless automated slot.

**The unblock is small and already 90% built.** The deterministic core is platform-agnostic:
- `runEvalSuite(opts, modelLabel)` in `src/utils/evalDriver.ts:28` takes `opts.generate: (messages) => Promise<string>` and `opts.systemInstruction`. It has **no DOM/browser dependency.**
- `evaluateResponse` (`src/utils/evalRunner.ts:87`), `EVAL_CASES`, and `reportToMarkdown` are pure TS.
- The only browser-coupled piece is *how `generate` gets its tokens*. In EvalPanel that's `engine.generate(...)`. Once that Node runner exists, **every future critic day is `node scripts/run-eval.mjs` in this same headless slot** — no human, no browser, no `Cache.add` blocker. The loop becomes self-sustaining, which is the whole point of the EVAL phase.

## E. Concrete Implementation Plan

### E.1 — Priority 1: `scripts/run-eval.mjs`

**Sketch (executor adapts to the real `transformersjs-engine.ts` gen params):**
```js
// scripts/run-eval.mjs
import { AutoTokenizer, AutoModelForCausalLM } from "@huggingface/transformers";
import { runEvalSuite, reportToMarkdown } from "../src/utils/evalDriver.ts"; // via tsx/vite-node
import { getSystemInstruction } from "../src/prompts/systemPrompts.ts";

const MODEL_ID = "onnx-community/gemma-4-E2B-it-ONNX";
const tokenizer = await AutoTokenizer.from_pretrained(MODEL_ID);
const model = await AutoModelForCausalLM.from_pretrained(MODEL_ID, { dtype: "q4" });

async function generate(messages) {
  const inputs = tokenizer.apply_chat_template(messages, { add_generation_prompt: true, return_tensor: true });
  const out = await model.generate({ ...inputs, /* same max_new_tokens / temperature / repetition_penalty as the engine */ });
  return tokenizer.decode(out[0].slice(inputs.input_ids?.dims?.at(-1) ?? 0), { skip_special_tokens: true });
}

for (const mode of ["freewrite","gratitude","checkin","thoughtrecord"]) {
  const report = await runEvalSuite({ systemInstruction: getSystemInstruction(mode), generate }, `Gemma 4 E2B (Node)`);
  writeFileSync(`docs/eval-runs/2026-06-01/${mode}.md`, reportToMarkdown(report));
  // also accumulate summary JSON
}
```
- **TS import in Node:** the repo uses Vite + `tsc`. Easiest path is to run the script with `tsx` or `vite-node` (add as devDep if absent) so it can import the `.ts` harness directly. Document the chosen runner in the script header. If onnxruntime-node isn't pulled in transitively, add `onnxruntime-node` as a devDep so Transformers.js uses native CPU instead of WASM (much faster).
- `--limit N` flag: slice `EVAL_CASES` (or pass `dimensions` + a per-dimension cap) so the smoke run is fast.
- Honor the existing KV-cache-reset discipline (`engine.resetContext()` analogue): construct a fresh generation per case — `runEvalSuite` already sends a full message array per case, and a Node `model.generate` call is stateless per call, so the `VectorInt`/`Cache.add` issues that plague the browser don't apply. Note this explicitly in the report (it's a side benefit of the Node path).

**Verify:** `npm run eval:smoke` prints 5 coherent responses and writes a valid 5-case report. Eyeball that the responses are real model text, not error strings.
