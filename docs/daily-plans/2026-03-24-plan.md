# QuietNote Daily Plan — 2026-03-24

## A. Today's Objective

Fix the model's broken multi-turn conversation and rambling responses — the two most visible quality issues a real user would notice within 60 seconds of using the app.

## B. Why This Matters

During live testing today, the model produced a 7+ sentence rambling lecture about embarrassment (repeating itself three times) in response to a simple anxiety journal entry, then gave an *almost identical* response to a completely different follow-up question about supplements. A user experiencing work anxiety would find this unhelpful at best, and frustrating enough to close the app. The guardrails and eval framework built over the last week are necessary safety infrastructure — but if the basic conversation doesn't work, none of it matters. Today shifts focus from safety tooling to the core user experience.

## C. Top 3 Priorities for Today

1. **Fix multi-turn response repetition by resetting WebLLM chat state between turns** — The model repeated its first response nearly verbatim on the second turn, ignoring the user's follow-up entirely. This suggests WebLLM's internal KV cache is not being properly managed when we build our own message arrays. The model needs to see the conversation history correctly, not replay cached generation.

2. **Enforce response length at the generation level, not just post-hoc guardrails** — The model generated 7+ sentences when the system prompt says 3-4. The current `max_tokens: 512` is far too generous. Reducing to ~150 tokens and tuning `temperature`/`top_p`/`repetition_penalty` will produce tighter, more focused responses at the source rather than relying on after-the-fact truncation.

3. **Improve guardrail console logging for debuggability** — The guardrails fired during testing but logged `[object Object]` and `Array(1)` instead of readable details. This makes it impossible to verify guardrail behavior during manual testing or debugging.

## D. Concrete Implementation Plan

### Priority 1: Fix Multi-Turn Response Repetition

**Root cause hypothesis:** WebLLM's `CreateMLCEngine` maintains an internal chat state (KV cache). When `chat.completions.create()` is called with a full messages array, the engine may be appending to its cached conversation rather than replacing it, causing the model to see duplicated context or stale state. The engine's internal state may need to be reset between calls.

**Exact changes:**
- In `src/App.tsx`, `replyInThread()` function (line ~348):
  - Before calling `e.chat.completions.create()`, call `await e.resetChat()` to clear the engine's internal KV cache. This forces the engine to process our full messages array from scratch rather than relying on stale cached state.
  - Alternatively, investigate `e.chat.completions.create()` with `{ stream: true, stateless: true }` or equivalent WebLLM option to disable state accumulation.
- In `src/hooks/useMLCEngine.ts`:
  - Expose `resetChat` from the engine if not already available.

**Where it lives:** `src/App.tsx` (replyInThread), `src/hooks/useMLCEngine.ts`

**Dependencies:** WebLLM API — check `@mlc-ai/web-llm` docs for `resetChat()` or stateless mode.

**How to test:**
1. Open app, send "I'm feeling anxious about work"
2. Wait for response
3. Send "What do you think about that?" or "Should I try supplements?"
4. Verify the second response acknowledges the follow-up and doesn't repeat the first response
5. Verify conversation history is visible in the chat

**What could go wrong:** `resetChat()` may clear the KV cache but also lose the system prompt, requiring re-injection. If so, we need to ensure the system prompt is always included in the messages array (which it already is via `buildMessages`). The main risk is increased latency per turn since the engine has to re-process the full conversation from scratch — but for a 2048-token context window, this should be negligible.

### Priority 2: Enforce Response Length at Generation Level

**Exact changes to `src/App.tsx`:**
- Reduce `maxTokens` from `512` to `150` (line 94). At ~0.75 words/token, 150 tokens ≈ 112 words ≈ 4-5 sentences. This hard-caps generation length at the model level.
- Add `repetition_penalty: 1.3` to the `chat.completions.create()` call to discourage the repetitive patterns observed (embarrassment defined three times).
- Consider reducing `temperature` from `0.5` to `0.4` for tighter instruction following.
- Update both `newSession()` and `replyInThread()` with these parameters.

**Where it lives:** `src/App.tsx`, lines 93-94 and the two `e.chat.completions.create()` calls

**Dependencies:** WebLLM must support `repetition_penalty` in the create options. If not, omit it and rely on `max_tokens` reduction alone.

**How to test:**
1. Send a journal entry and verify the response is 3-5 sentences, not 7+
2. Verify responses still end with a reflective question (the system prompt instructs this)
3. Verify no response is cut off mid-word (truncateToLastSentence should handle this)
4. Test 3+ different prompts to ensure variety

**What could go wrong:** 150 tokens may be too restrictive for some responses, cutting off the reflective question. If testing shows this, increase to 180-200. The key constraint is that responses should never exceed 5 sentences.

## F. UX & Design Review

### How the app feels as a product:
The app loads successfully, looks clean, and the privacy-focused positioning is clear. However, the core interaction — sending a message and getting a response — is disappointing. The model's responses feel like reading a psychology wiki article, not talking to a supportive companion. A real user having a bad day would find the rambling, repetitive response frustrating rather than comforting.

### What a first-time user would think:
1. Loading screen: "OK, it's loading something, 36 seconds is a bit long but I can wait"
2. First message: "This response is really long and doesn't address what I said. Did it even read my message?"
3. Second message: "It just repeated itself? Is this thing broken?"
4. At this point, the user would likely close the app.

### Biggest UX gap right now:
**Response quality.** The model's output is the product. Everything else — UI, mood tracking, sessions — is scaffolding around the conversation. If the conversation doesn't feel natural and helpful, no amount of features will save the experience. The two biggest sub-issues are: (1) responses are too long and unfocused, and (2) multi-turn doesn't work, making the app feel like it's not listening.
